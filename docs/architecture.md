# Architecture

## Layers

```
core/        platform-neutral: asb CLI, model + validator, stage gates, checks, policy hook,
             plugin skills / agent / commands
packs/       how to build: turn an approved model into an app and verify it   (sidecar-django)
connectors/  how to reach a business system, read-mostly                      (erpnext)
solutions/   one folder per client solution: the artefacts of all six stages
```

The core never imports or names a pack, a framework or an ERP. It finds packs and connectors by folder name and loads them from their YAML descriptors (`packs/<name>/pack.yaml`, `connectors/<name>/connector.yaml`), importing the package named by `entry` from that folder. A test keeps `core/` free of those names. Neutral vocabulary is used instead: field types, permissions, and external *kinds* such as `outbound_shipment`, which a connector maps to the system's own document names.

The tool lives in `core/tool/asb/`:

| Module | Job |
|---|---|
| `cli.py` | Typer commands |
| `model.py`, `validate.py` | `solution.yaml` schema and cross-checks (references, workflow reachability, traceability, pack capabilities) |
| `status.py` | `status.json`, approvals, stage gates, verify-round counter, audit log |
| `plugins.py` | Pack and connector loaders; `GenerateResult`, `VerifyResult`, `CheckResult` |
| `connector.py` | The neutral `Connector` protocol and errors (also vendored into generated apps) |
| `discover.py` | Builds `discovery.md` from a connector |
| `checks.py` | Static guardrail checks and policy loading |
| `verify_report.py` | Renders `verify-report.md` |
| `core/policy/` | `policy.yaml` and the PreToolUse `hook.py` |

## The pipeline and gates

Stages: requirements, discovery, design, build, verify, release. `status.json` holds each stage as `todo` or `done`, the approvals (kind, who, when, and for design the model version and SHA-256), and `verify_rounds`. `asb gate <name> <stage>` (and the stage commands themselves) refuse when:

| Stage | Refused unless |
|---|---|
| design | a requirements approval exists |
| build | a design approval exists and `design/solution.yaml` still hashes to the approved value |
| verify | build is done, `design/solution.yaml` still hashes to the latest approved value, and fewer than 3 verify rounds have run |
| release | verify is done and a client approval exists |

Approvals (`requirements`, `design`, `client`, `golive`) are recorded only by `asb approve`, run by a person. `status.json` also records `built_hash`, the design hash the last build used. A build always sets verify back to `todo`, but resets the 3-round counter only when the approved design differs from `built_hash` (a new design approval); rebuilding an unchanged design does not grant new rounds. `asb approve <name> design` runs the validator (with the pack's capabilities) and refuses a design with issues; an empty `--by` is refused. A failed discovery or verify never leaves its stage marked done.

## Ownership model

The pack separates two kinds of file in `app/`:

- **Generator-owned**: models, migrations, API, permissions, workflow, UI metadata, matrix tests, vendored connector. They start with `# GENERATED by asb — do not edit; regenerate from solution.yaml` (`//` in TypeScript) and are rewritten on every build.
- **AI-owned**: `rules/rNN.py`, `reports/<name>.py`, `tests/test_at_NN.py`, and underscore-prefixed helpers. Written once as stubs, never overwritten, never carrying the header. If the model drops a rule or report, its leftover file is an orphan and the build fails loudly rather than guess.

Generation writes `app/.asb-manifest.json` (SHA-256 of every generated file) and an anchor copy of the manifest's hash in `.asb/manifests/<solution>.sha256`, outside the app, so an edited manifest is also detectable.

## What `asb check` and `asb verify` do

`asb check` is static: policy checks over the app. The names are `EVAL` (eval/exec), `RAW_SQL` (SQL built from strings), `SECRET` (hard-coded secrets), `NO_PERMISSION` (API views without permission classes; pack-configured) `HEADER_TAMPERED` (a generated file edited, removed or unknown, or the manifest edited) and `UNLISTED_CONFTEST` (a `conftest.py` under `app/backend` that is not in the manifest). A pack's policy can only add to the deny lists, checks and `skip_paths`; it cannot extend `ignore_paths` or `build_output`.

`asb verify` asks the pack to run all evidence and writes `verify-report.md`. For `sidecar-django`: acceptance mapping (every acceptance test has a passing test), the test suite, permission matrix, workflow matrix, reports, static checks, frontend build and a UI smoke walk through each role. A check that cannot run reports `skipped` with a reason in the report. Skips do not all behave alike: a skipped `frontend_build` or `ui_smoke` (no npm, no browser, registry unreachable) is reported but does not fail verify; a skipped acceptance test is never evidence for its acceptance test; a matrix case skipped as `sample-incomplete` fails its matrix check. The permission matrix, workflow matrix and reports checks also compare the executed cases with the cases the model implies (roles x entities x permissions, transitions x roles, one per report) and fail, listing them, when any is missing from the test run. Any `fail` makes the run fail and sets verify back to `todo`. The test run ignores `PYTEST_*` environment variables, and `asb check` flags any `conftest.py` under `app/backend` that the generator did not write (`UNLISTED_CONFTEST`).

## Guardrails

Packs may only tighten the core policy: lists are unioned, and the core value wins for any other conflict. The PreToolUse hook (`hooks/hooks.json` runs `core/policy/hook.py`) applies while a solution is active (`.asb/active`, set by `asb new`, `asb build` or `asb use`):

- file-writing tools may only touch `solutions/<active>/`, and never `status.json`, `audit.log`, `exceptions.yaml`, the manifest or anything under `.asb/`;
- Bash commands matching `deny_commands` are blocked (recursive forced delete, `git push`, `docker system prune`, HTTP DELETE, `DROP TABLE`, `asb approve`, `asb use`, touching `.asb`, redirects onto protected files);
- unexpected errors block (fail closed); blocks are logged to `audit.log`.

This is a **guardrail, not a sandbox**. Bash can still reach arbitrary paths through interpreters or tools the deny list does not know, and MCP tools are not covered by the hook matcher. It reduces mistakes; it does not contain a hostile actor. Human approvals and review remain the real controls.

## Credentials

Connectors read credentials only from `ASB_ERP_URL`, `ASB_ERP_API_KEY`, `ASB_ERP_API_SECRET`. Nothing is stored in solution files; the `SECRET` check looks for leaks.

## Plugin layer

`.claude-plugin/plugin.json` points at `core/skills` (one per stage), `core/agents` (`asb-reviewer`, read-only, writes only `review.md`), `core/commands` and `hooks/hooks.json`. Skills call `asb`; they are neutral and refer to "the pack" and "the connector".
