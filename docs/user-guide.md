# User guide: building Gate Pass

This walks through the pilot solution in `solutions/gate-pass/`. Commands use `uv run asb`; inside Claude you can describe the same steps in plain language and the stage skills run the commands. Approvals are always typed by a person.

**Gate Pass:** a vehicle taking goods out or bringing goods in carries a pass. Store staff raise it against a submitted ERP Delivery Note (out) or Purchase Receipt (in); security approves or rejects at the gate; a manager reads the register. The ERP is only read.

## 0. Set up

```sh
uv sync
uv run asb --help
```

In Claude Code, install the plugin (see the README). Anywhere below, `asb status gate-pass` shows where you are and `asb gate gate-pass <stage>` says whether a stage may start.

## 1. Start the solution

Say: "A client wants a gate pass module." Claude starts the `asb-requirements` skill, or run `/asb-new gate-pass`:

```sh
uv run asb new gate-pass --pack sidecar-django --connector erpnext
```

This creates `solutions/gate-pass/` (`status.json`, `audit.log`, empty `requirements.md`, `discovery.md`, `design/`) and makes it the active solution, so the hook confines the AI to that folder.

## 2. Requirements

Claude interviews you one question at a time and writes `solutions/gate-pass/requirements.md`: Goal, In the client's words, Users and roles (store_user, security, manager), Current process and pain points, Volumes (about 40 passes a day), Must have (7 items), Nice to have, Open questions. Read it, correct it, then approve in your terminal:

```sh
uv run asb approve gate-pass requirements --by "Your Name"
```

## 3. Discovery

Set the connection in your shell (never in chat or files): `ASB_ERP_URL`, `ASB_ERP_API_KEY`, `ASB_ERP_API_SECRET`. Then:

```sh
uv run asb discover gate-pass --kind outbound_shipment --kind inbound_receipt
```

`discovery.md` lists each external kind with its system document, fields available, sample records and status, plus gaps. For Gate Pass both kinds were found (Delivery Note, Purchase Receipt) and the result is "None" for gaps. This pilot's file came from a recorded sample, so a real project re-runs discovery against the live system. If connection fails, the file says so and the stage stays not done.

## 4. Design

Requirements must be approved first (`asb gate gate-pass design`). Claude writes, under `solutions/gate-pass/design/`:

- `process-map.md`: Mermaid flow from creating a pass to closing it.
- `solution.yaml`: entities `gate_pass` and `gate_pass_line`; workflow draft, pending_security, approved, rejected, closed; roles; rules R1 (reference must be submitted in the ERP) and R2 (quantities within the document); the `gate_register` report; acceptance tests AT-01 to AT-06.
- `acceptance.md`, `plan.md`, and `design-review.md` (decisions with their sources, risks, open questions).

```sh
uv run asb validate solutions/gate-pass
```

Validation checks references, workflow reachability, that every rule, transition and role permission is covered by an acceptance test, and that the pack supports every feature used. Fix issues until it prints `OK: no issues`. Review the files, then approve:

```sh
uv run asb approve gate-pass design --by "Your Name"
```

The approval records the model version and SHA-256 of `solution.yaml`. If the file changes later, `asb build` refuses until you approve again.

## 5. Build

```sh
uv run asb build gate-pass
```

The pack generates `app/` (Django backend, React frontend, Compose file) and stubs for the AI-owned files: `backend/rules/r1.py`, `r2.py`, `backend/reports/gate_register.py`, `backend/tests/test_at_01.py` to `test_at_06.py`. Claude implements only those. Generated files start with `# GENERATED by asb — do not edit; regenerate from solution.yaml` and are never edited by hand. Then:

```sh
uv run asb check gate-pass
```

## 6. Verify

```sh
uv run asb verify gate-pass
```

This writes `verify-report.md`. For Gate Pass round 1: acceptance mapping (6 tests mapped), tests, permission matrix, workflow matrix, reports, static checks, frontend build and UI smoke all pass. If something fails, Claude fixes it and you run verify again; after 3 rounds the gate stops the loop and a person decides. After a pass, Claude dispatches the `asb-reviewer` agent, which writes `review.md` with findings by severity. The review is advice; you decide.

## 7. Release (manual)

Release automation is not built (sub-project 3). The `asb-release` skill gives a checklist: change summary, UAT on staging, then `asb approve gate-pass client --by "<client contact>"`, backup and rollback preparation, then `asb approve gate-pass golive --by "<name>"`. A person deploys.

## Reference

| File | Meaning |
|---|---|
| `status.json` | Stages, approvals, verify rounds (written by `asb` only) |
| `audit.log` | One line per event |
| `design/solution.yaml` | The approved model; source of all generated code |
| `app/.asb-manifest.json` | Hashes of generated files, checked by `asb check` |

To change who the hook confines the AI to, run `asb use <name>` yourself (`asb use --clear` removes the guardrails; use with care).
