# Stage 4: Build

**Purpose:** generate the app from the approved model, then implement the AI-owned parts and pass the static checks.

**Inputs:** approved `design/solution.yaml`, `acceptance.md`, `plan.md`.

## Steps

1. `asb gate <name> build` must print `OK` (design approved and unchanged). If not, stop and report the reason.
2. `asb build <name>`. The pack writes generated files and one stub per AI-owned file, and keeps any AI-owned file that already exists.
3. Implement **only AI-owned files** in `solutions/<name>/app/`:
   - one function per business rule (`rules/rNN.py`, matching the rule ids),
   - report logic (`reports/<name>.py`),
   - acceptance tests (`tests/test_at_NN.py`, one per acceptance test, marked with its id),
   - helpers, which must be named with a leading underscore (`rules/_helpers.py`). Any other file with a rule or report name that the model no longer asks for is an orphan and fails the build.
4. Never edit a generated file. They start with `# GENERATED by asb — do not edit; regenerate from solution.yaml` (`//` in TypeScript). If one needs to change, change `solution.yaml`, ask the human to re-approve the design, and rebuild.
5. Follow `plan.md`. Read connected systems only through the vendored connector; credentials only from the environment.
6. `asb check <name>`. Fix every reported issue (unsafe eval, raw SQL formatting, secrets, endpoints without permission classes, tampered generated files) and re-run until it prints `OK: no issues`.

## Outputs

`solutions/<name>/app/` with implemented AI-owned files; stage 4 marked done by `asb build`.

## Gate

`asb check <name>` passes. Every build sets verify back to `todo`, but the 3-round fix-loop counter resets only when the human approves a changed design (the approved design hash differs from the one the previous build used). Rebuilding an unchanged design keeps the rounds.

## Boundaries

- Never run `asb approve` or `asb use`; ask the human to.
- The hook confines writes to the active solution and blocks edits to `status.json`, `audit.log` and the manifest. It is a guardrail, not a sandbox: do not try to work around it.
- No delete, submit or cancel against the client's system; writes only for operations the approved model lists as `write:<operation>`.
- Knowledge base and policy layers arrive in sub-project 2; until then cite spec/discovery sources manually in design-review.md.
